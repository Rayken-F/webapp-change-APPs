規則主檔：Rayken-F/webapp-change-APPs / RULER.txt
適用：本專案的程式修改、除錯、版本發布、後端交付與驗收說明。
本文件保存使用者要求，不代表已改寫 ChatGPT 跨聊天室記憶或自動載入設定。

【新聊天室／接手任務的起始流程】
接手本專案時，先完整讀取本 RULER，再讀本次直接相關的交接內容、使用者最新指示與實際程式版本。不要只靠上一段摘要或舊記憶猜測。
查證範圍限於本次需要的檔案與部署，不為小改動反覆掃描無關模組。
未取得必要規則、程式或權限時，應明確指出缺口；不得宣稱已讀取、已更新記憶或已部署。
本文件不授權擴大修改範圍；使用者後續明確更正的專案需求應同步維護，其他既有規則仍保留。

【一、只修改本次必要範圍，其餘不准動】
1. 先讀取實際使用版本，確認本次需要修改的檔案、函數與相依關係。
2. 只修改需求或修正故障所必要的段落。不得順便重構、改版面、重新命名、重排欄位、格式化全檔、清理舊程式或改其他模組。
3. 如修正確實需要擴及未授權的共用流程、資料結構或其他模組，先列明理由、影響與風險，取得確認後再改。
4. 提交前核對差異；交付時明列已修改檔案與未修改範圍。不得用舊版本完整覆蓋造成已驗收功能倒退。
5. 保留既有掃描資料、RT 歷程、待傳操作與固定連結。不可用清除網站資料、刪批次或重掃來掩蓋 BUG。

【二、交付必須可用、可核對，驗收指示必須清楚】
1. 先確認工具、存取權限、目前前後端版本與必要資料，再說明能完成的範圍；不可先保證、耗時後才交付無法使用的結果。
2. 明確區分「程式已寫好」「已提交 GitHub」「部署成功」「前後端相容」「使用者驗收通過」。未完成的階段直接標示，不用修改網址參數或版本文字冒充發布完成。
3. GitHub 任務須實際發現並嘗試可用的讀寫工具，不能憑上一聊天室印象宣稱只能讀取；遇到實際限制時說明失敗步驟，不反覆空查或虛報成功。
4. 除錯先讀錯誤證據與完整相關程式。第一次修正未解決時，取得目前實際使用的完整相關 CODE 與必要日誌；已可從 GitHub 或本聊天室取得的資料由助手自行讀取，不重複索取。
5. 模擬測試、語法檢查與實際後端／手機驗收必須分開說明。真實 CTN 驗收不能偷偷退回模擬 IQC 或模擬收據。
6. 驗收說明固定包含：使用哪個網址及版本 → 頁面／選單位置 → 按鈕確切名稱 → 輸入內容 → 正確畫面或後台欄位 → 異常時提供哪段錯誤。不可只說「去測一下」「重新部署」或「看後台」。
7. 依實際改動提供最短必要驗收路徑；已通過項目不無故歸零。需要回歸驗收時只列受影響部分並說明理由，不另要求其他人重新驗收。
8. 不無故新增流程、模式、前置條件、檔案或獨立專案；不讓使用者反覆追問同一個未交付項目。不承諾訊息結束後仍在背景開發。
9. 確認問題與處理能力後，優先完成已授權的實際工作，而不是反覆回覆規格、道歉或要求再次說「開工」。無法完成時立即交代具體原因、已完成與未完成項目。

【三、固定分工】
助手（G神）：負責版本管理、RC／正式分支、前後端版本配套、GitHub 前端程式修改、提交、發布及部署結果核對；負責準備後端更新程式與精確操作說明。
使用者：負責 Google Apps Script 後端 CODE 套用／更新部署，以及現場驗收與正式上線同意。
前端不得預設交由使用者上傳或覆蓋。後端不得宣稱助手已在使用者 Google 帳戶部署；需由使用者實際操作。
流程：助手修改與內部檢查 → 助手發布 DEMO 前端並交付配套後端 → 使用者更新後端與驗收 → 使用者確認後正式發布。
正式發布核對不等於重跑整份驗收；不因使用者是驗收人就跳過必要身分／權限驗證。

【延續的交付與安全邊界】
超過 10 行程式以 .txt 檔交付，不在聊天室貼長 CODE；前端更新仍由助手在 GitHub 完成，下載檔不代表轉交更新責任。
sw.js 不另提供下載檔，必要變更由助手處理並告知版本。
除本次明確授權外，不改 Response 欄位順序／Timestamp、既有 ERP API 連結、不重做 Dashboard、不改其他正式模組。
DS 工作台沿用單一登入；權限不可寫死前端。OQC 只讀 IQC 來源，不因 OQC 更改 RT 而回寫 IQC。
DEMO 通過不等於可自行正式上線；以使用者明確同意為準。
