# IQC 影像 RC31.9 / OCR-S10-20260924

固定入口：https://rayken-f.github.io/webapp-change-APPs/ds-app-grinding-recovery-rc/v31.html
發布狀態以 Pages 核對紀錄為準；本輪仍是隔離 RC，正式 IQC 寫入維持鎖定。

## 本輪原因與修改

使用者 RC31.8 紀錄顯示開始指令 accepted、引擎初始化 73／90／95ms 成功，但 preprocess 在 1ms 失敗，並出現 STORAGE_UnknownError。所見失敗輪沒有進入 recognize；不能把它歸因為缺 RT 或單純按鈕未觸發。附檔於後一輪途中截斷，不推定後續結果。

原程式在 PROCESSING、辨識成功及失敗時，反覆把同一筆資料庫 Blob 重新寫入；錯誤事件沒有 code 時誤歸為 WORKER_ERROR，且失敗狀態再次寫入失敗會遮蔽第一個原因並終止整批。這些為已確認的程式缺口。WebKit 有相近的 Blob 讀取／覆寫缺陷紀錄，但不能僅憑 UnknownError 斷言使用者的 iOS 就是特定版本缺陷或儲存已滿。

- RC31 新照片以 ArrayBuffer 位元資料存於原 photos store，同時保存 MIME 與縮圖；使用時才建立暫時 Blob。不改 DB 名稱、版本、照片 ID、批次 ID 或刪除資料。
- 舊照片辨識前先讀出完整 bytes，長度核對成功後才轉存。舊結果、人工歸類、歷史、區域與建立時間保留。舊照片讀不到時不覆寫原列；本頁顯示該照片失敗，後續照片仍繼續，診斷紀錄保留。
- 本機歸類／合併、預覽及手動 Cloud 補辨識使用相同照片讀寫介面。共享 intake 提供新格式回讀，舊 RC 原有欄位及分支保留。佇列只持有 metadata／縮圖，不留整批原圖。
- 區分 IMAGE_READ_ERROR、DECODE_ERROR、IMAGE_PREPROCESS_ERROR 與 worker 故障；先記錄照片失敗，再保存狀態。第二次存檔錯誤另記 failure_save／primaryCode，不再冒充啟動失敗。整個資料庫無法存檔仍停止並明示，不能假稱結果已保存。
- 引擎、模型、觸控啟動及辨識規則不更換；只調整 decode 錯誤分類。單張故障不銷毀健康引擎；原 worker 故障的一次有界恢復保留。

## 限制

已經讀不到的舊 Blob 無法憑空重建；保留原批次及候選，不要求清網站資料。若原照片仍在相簿，可另加回該照片；核對來源後再處理重複，不自動刪除既有紀錄。讀不到舊照片的狀態在本頁提示，重新開頁會再檢查，原列保持未覆寫。

更改儲存表示方式沒有提高 OCR 字元準確率的宣稱；既有 5/S 等警示及人工核對仍保留。使用者本輪確認批次欄位通過、單張啟動改善；多張辨識未通過。CG 本機測試與 iPhone 現場验收分開記錄，不承諾所有裝置及任意照片 100%。

## 最短驗收

1. 重整固定 RC 入口，確認 RC31.9 / OCR-S10-20260924；更多 → Honeywell 影像。原批次、照片、人工歸類應仍在，已驗收批次欄位不另重測。
2. 原批次只按一次「開始辨識未完成照片」。讀得到的舊照片應依序處理；若某張本機內容讀不到，應清楚標出該張，仍往下一張，不顯示 WORKER_ERROR。
3. 另用原本三張照片加入「新批次」（保留舊批次），一次加入、一次開始並保持前景，確認依序處理。已完成照片不重跑。必要時人工指定 RT，再重整確認候選／照片／歸類保存。
4. 若仍卡住，頂欄「進度／操作」→「複製辨識紀錄」。不要連按或清網站資料。紀錄有 read_image／image_source、preprocess、pass、photo_failed、failure_save，可區分讀圖、引擎與儲存。

Google 後端、正式 OQC／Grinding／登入／權限／業務資料未修改，沒有自動 Cloud 送圖。正式 IQC 建檔仍未開放。

工程參考：[WebKit Blob 重複儲存問題](https://bugs.webkit.org/show_bug.cgi?id=240216)、[WebKit IDB Blob 路徑修正](https://lists.webkit.org/pipermail/webkit-changes/2025-July/320667.html)。這些為對照資料，不代替本次手機根因證明。
